# 主数据巡检走"确定性脚本算 + AI 只判 shortlist"，不让 agent 眼检原始数据

定时巡检里"找出可疑 SKU"这一步由**确定性检测脚本**完成：脚本调 `in3_client` SDK 拉服务端数据、在子进程内算完信号 A/B/C/D，只回一份几十条的 **shortlist**。AI（被定时触发体的提示词驱动）**只对 shortlist** 做根因判读、排序与写报告，**不把原始 PO/价格记录数据喂进上下文、不靠"眼睛找异常"**。

关联：[CONTEXT.md](./CONTEXT.md)。

## Why

触发本功能的事故复盘里，朱政的原话是"把上下文喂给 AI，让 AI 帮我们找出可能有问题的 SKU"——那是**应急人工跑一次**的形态。要做成**定时巡检**，纯 AI 眼检会同时踩两个致命雷：

1. **上下文爆炸**。全量物料 × PO 历史正是 `in3_client` SDK 当初要解决的问题：北极星任务实测原始数据 540 万 token / 15.8 MB，SDK 子进程算完只回 565 token / 1.4 KB（省 99.99%）。把原始数据喂进提示词，一次就炸。
2. **结果漂移、不可复现、不可审计**。agent 每次"重新推理找异常"，同一批数据这次报 8 条、下次报 5 条。Sourcing 要据此核验改价、朱政要据此追"上周报过的这条这周怎么没了"——巡检产物**必须可复现**，否则没法信、没法追责。这比检测算法不够准更致命。

把"算"（确定性、可复现、省 token）与"判"（AI 的语义灵活性：解释根因、读懂描述里的"250根/包"、措辞）分层，正是 `in3-cli` 的 code-mode 本意，也对齐 `in3-cli-doctor` 的 `probe→judge→aggregate→report` 套路。

## Considered alternatives

- **纯 AI 判读（agent 自己多次拉数据集进上下文、眼检找异常）。** 最贴朱政"喂给 AI 让 AI 找"、最灵活。**否决**：上下文爆 + 结果每期漂移、不可复现、不可审计——与"定时巡检"的可信前提直接冲突。
- **纯确定性脚本（AI 只当调度，报告全由脚本产出）。** 最可复现。**否决**：丢了 AI 的语义判断——读懂物料描述里非结构化的"N 根/包"文本、对 shortlist 解释根因、对边界 case 给人话。这些恰是 rule #1 信号 C 与报告可读性的关键。
- **分层：脚本算 + AI 只判 shortlist（选用）。** 确定性打底保证可复现/省上下文/可审；AI 判读保留语义灵活性。两者边界清晰：脚本吐 shortlist（几十条），AI 不碰原始数据。

## Consequences

- 检测器（`mdm_sentinel.py`）是**确定性的**，可单测、可拿田野那份 Excel 做 ground truth 回归；信号阈值改动有据可查。
- 定时触发体的**提示词只需指挥 AI**："调 `execute_code` 跑 `mdm_sentinel.py` 拿 shortlist → 逐条判根因/排序 → 套 HTML 模板出报告"——提示词不承载检测逻辑，逻辑在脚本里收口。
- AI 判读层的**输入被严格限定为 shortlist**（几十条），上下文恒定可控，与物料总量解耦。
- 代价：检测逻辑沉到脚本后，"加一种新异常模式"要改代码（加一条规则）而非改提示词——但这正是可复现性想要的刚性。
- 与"框架"形态一致：脚本侧就是 rule registry + scorer，AI 侧是 aggregate/report；未来加 rule #2（如"有交易无价格记录"）在脚本侧注册即可，AI 判读层不变。
